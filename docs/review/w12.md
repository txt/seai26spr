# AI Agents in SE: Glossary & Review Questions

---

## Glossary

### Agent Fundamentals

**AI Agent**
: An LLM augmented with tools and a loop that lets it act, observe, and revise; distinct from a plain LLM which only transforms text with no memory or external access

**Multi-Agent System**
: An orchestrator that delegates to focused sub-agents, each with a defined role; agents share findings and the system adapts to task complexity

**Agentic Orchestration**
: Dynamic, conditional execution of sub-agents; skips steps for simple cases, triggers deeper deliberation for ambiguous ones; contrasts with rigid prompt chaining which pays full reasoning cost for every input regardless of complexity

**Synchronous vs. Asynchronous AI**
: Synchronous = human-in-the-loop, one prompt at a time (Copilot, ChatGPT); Asynchronous = event-triggered, runs in CI/CD pipeline without human prompting, scales compute while the engineer sleeps

**Principle of Least Privilege (for agents)**
: An agent should have access to exactly the tools and filesystem paths it needs — no more; enforced via sandboxing, network blocks, resource limits, and tool whitelisting

---

### Fuzzing & Oracles

**Differential Fuzzing**
: Feed the same input to multiple implementations of the same spec; disagreement between outputs signals a potential functional bug

**Differential Oracle**
: The judge that decides whether a cross-implementation discrepancy is a true bug or allowed divergence; often the primary bottleneck in large-scale fuzzing pipelines

**Oracle Problem**
: Generating test inputs is largely solved; judging outputs is not — at production scale, most findings are noise, and manual triage is prohibitively expensive per finding

**Allowed Divergence**
: Behavioral differences between implementations that are valid under the spec (e.g., host-defined functions); a naive rule-based oracle cannot distinguish these from true bugs, causing false positive rates to explode

---

### Agent Design Principles

**Tools Over Agents**
: The value of an agentic system is determined more by what it can *access* than by how many agents it has; a model that can run code, query a live document, or search a database is categorically more reliable than one reasoning from memory alone

**Decompose, Don't Monolith**
: Smaller, focused agents with clear roles reduce hallucination compared to one large model juggling everything; each agent should have a single well-defined job

**Architecture Beats Scale**
: Good system design with a smaller model can outperform a larger model used naively; the right response to poor quality is usually a smarter architecture, not a bigger model

**False Positive Rate (FPR)**
: Fraction of non-bugs incorrectly flagged as real issues; keeping FPR low is a prerequisite for any autonomous downstream action (e.g., filing tickets, opening PRs) — a high FPR erodes trust and gets agents banned

---

### Labeling & Evaluation

**Label-Starved Domain**
: A problem space where ground truth is rare or expensive to obtain, making standard train/test evaluation difficult; requires creative approaches to generate surrogate labels at scale

**Semi-Supervised Labeling**
: Generate a large finding set → group by coarse signal → cluster semantically → have humans label only cluster representatives → propagate labels to the rest; reduces labeling cost dramatically

**Medoid**
: The actual data point closest to the center of a cluster; the one item a human expert labels to represent the whole cluster in a semi-supervised pipeline

**Eval (Evaluation)**
: A behavioral benchmark for an agent system, measuring statistical reliability (recall, FPR, precision) rather than deterministic pass/fail; the agentic analogue of a unit test suite — you test the agent's *behavior*, not its code

---

### Protocols & Infrastructure

**Model Context Protocol (MCP)**
: Anthropic's open standard for agent–tool communication; a JSON-RPC client–server protocol where servers expose Tools, Resources, and Prompts; eliminates the need for each team to reinvent tool interfaces — "USB for agent tools"

**Agent-to-Agent Protocol (A2A)**
: Google's open protocol for agent–agent delegation across organizational or system boundaries; agents publish Agent Cards declaring their capabilities, enabling runtime discoverability and cross-org task handoff

**Agent Card**
: A JSON manifest an agent publishes about itself, declaring what it can do, its input/output schema, and authentication requirements; enables other agents to discover and delegate to it dynamically

**Audit Trail / Reasoning Trace**
: A logged record of every tool call and sub-agent decision in an agentic workflow; makes decisions reproducible, debuggable, and verifiable — increasingly required for regulatory compliance and maintainer credibility

## Review Questions

**Q1**
(a) Define the three ingredients of an AI agent and explain why each is necessary. What is the key difference between an *assistant* and an *agent*?
(b) A monolithic LLM call is simpler to implement than a multi-agent system. Identify two structural failure modes that emerge when scaling a single LLM prompt to high-volume, automated classification tasks, and explain why switching to a larger model does not fix them.

**Q2**
(a) Explain the oracle problem in differential fuzzing. Why is generating inputs considered "solved" while judging outputs is not?
(b) Give a concrete example of *allowed divergence* between two implementations. Walk through why a rule-based filter fails to handle it, and what an agent-based approach can do differently.

**Q3**
(a) Explain the "tools over agents" principle. What does it imply about where to invest effort when designing an agentic system?
(b) Under what circumstances might adding a sub-agent still be justified over adding a tool? What tradeoff are you making?

**Q4**
(a) What is a label-starved domain, and why does it make standard ML evaluation difficult?
(b) Describe a semi-supervised labeling pipeline that uses clustering to reduce manual annotation cost. What is the key assumption being made when you propagate a label from a medoid to an entire cluster, and when does that assumption break down?

**Q5**
(a) What is the "architecture beats scale" principle? Construct an argument for why good system design with a smaller model can outperform a larger model used naively.
(b) A colleague proposes replacing a custom domain-specific agent with a general-purpose commercial agent (e.g., Claude Code, Codex) to avoid building infrastructure. What are three concrete failure modes to evaluate before making that decision?

**Q6**
(a) Distinguish MCP from A2A: what communication problem does each solve, and what is the rough transport/format of each?
(b) Describe a realistic enterprise incident-response scenario where multiple agents delegate across system boundaries. Identify which steps use tool calls (MCP-style) and which use agent delegation (A2A-style), and explain where a human decision is irreplaceable.

**Q7**
(a) Define the "Automation Layer Cake" tiers. Give one concrete SE task per tier and explain what makes the highest tier resistant to automation.
(b) The lecture argues the most valuable future skill is writing unambiguous specifications, not writing boilerplate code. Build an argument for this claim. What happens to a multi-agent system when the specification it depends on is vague or incomplete?

**Q8**
(a) What is an *eval*, and how does it differ from a traditional unit test? Why does the shift to agentic systems force engineers to invest more in evals?
(b) Explain the relationship between False Positive Rate and autonomous action. At what point does a high FPR become a hard blocker for a downstream automated step, and what architectural levers exist to reduce it?
